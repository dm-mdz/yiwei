| 项 | 内容 |
|---|---|
| 版本 | v0.9（按 macOS 上已做出来并经你验收的实际情况更新） |
| 状态 | **开发中**：macOS 的输入法和截图（含文字标注、点选窗口、长截屏）已做完，其中长截屏等新加的三样待你验收；键鼠共享、Linux、Windows 未做 |

---

## 1. 道

**Windows、macOS、Linux 三个系统我都在用。新开一台电脑，装这一个工具，三个日常操作上的痛点就都解决了，不用再折腾别的。**

## 2. 需求（就这三条）

| # | 痛点 | 要的结果 |
|---|---|---|
| 1 | macOS 和 Linux 上，不能用 Shift 切换中英文输入法 | 按一下 Shift 就在中英文之间即时切换，手感和微信输入法一样。做法也和它一样：自己做一个最小的输入法，Shift 只切内部状态 |
| 2 | macOS 和 Linux 上截图不好使 | Shift+Ctrl+A 截图：自由框选、涂鸦标注、长截屏 |
| 3 | 多台电脑各用各的键鼠，东西传不过去 | 一套键鼠跨屏幕用；复制粘贴互通；复制的文件能传到另一台 |

**各系统做什么**

| | macOS | Linux | Windows |
|---|---|---|---|
| 输入法（Shift 切换中英文） | 做 | 做 | 不做（系统本来就支持） |
| 截图 | 做 | 做 | 第一版不做（系统上已有能用的）；以后想要三个系统手感一致，再把同一套截图搬过去 |
| 键鼠共享、复制粘贴、文件传输 | 做 | 做 | 做 |

## 3. 法（判断标准）

| 编号 | 标准 |
|---|---|
| F1 | 只解决第 2 节的三个痛点，不照别的产品加功能 |
| F2 | 轻到无感：常驻占用极小；没开的功能不加载；不弹窗（系统强制的授权弹窗除外）、不联网、不采集；几乎不用配置 |
| F3 | 装上就够：一次安装、一个图标、开箱可用 |
| F4 | 稳比多重要：功能要么始终成立，要么明确告知何时不成立；平台规则不允许的不硬做 |
| F5 | 自己说了算：MIT 开源；数据只在本机和局域网 |
| F6 | 考虑成本：能用系统能力和宽松协议开源组件的就用；三个系统尽量共用一套代码 |

### 4.2 输入法（macOS、Linux）

| 编号 | 段 | 功能 | 级别 | 验收标准 |
|---|---|---|---|---|
| I1 | 切 | 单击 Shift 在中英文之间切换（切的是输入法内部状态，不是切换系统输入法） | P0 | 即时生效；Shift+字母打大写不误触发 |
| I2 | 转 | 全拼拼音、整句输入、中英文标点、自动学习词频（引擎自带） | P0 | 日常聊天写文档流畅 |
| I3 | 转 | 自带基础词库，装上就能离线打字 | P0 | 不联网也能正常打字 |
| I4 | 显 | 候选窗：单行、每页 7 个、跟光标、跟随深浅色、自有配色（不用微信绿）；单击 Shift 时在光标旁闪一下“中/英”小块 | P0 | 不闪烁、不抖动、不遮挡 |
| I7 | 转 | 整句：三个字以上的输入，按词频另算整句，和引擎首选不同时放在最前面 | P0 | 日常短句首选更准，不改错原本对的 |
| I6 | 转 | 纠错：相邻字母敲反、多敲、少敲、按到邻键，纯本地。纠错结果只放候选第二位，不抢第一位；正常输入、没打完的输入、全拼简拼混着打都不打扰 | P0 | 常用词正常输入不出现多余候选 |
| I5 | 转 | 增强词库可选下载 | P1 | 下载失败有提示 |

做法和微信输入法一样：它本身就是系统里的一个输入法，按 Shift 时系统输入法不变，只是内部从“查词”变成“按键直通”。所以切换即时，不需要额外的系统权限。只做上表这些，别的输入法功能一概不加。

## 5. 明确不做

| 不做的 | 原因 |
|---|---|
| 输入法里除了打字和 Shift 切换之外的功能（表情、常用语、双拼等） | 你要的只是打字顺、Shift 能切，没别的 |
| 键位映射（把 Mac 快捷键改成 Windows） | 平台规则下做不稳；你的决定：苹果就按苹果的用 |
| 录屏、水印、钉图、问 AI、语音、剪贴板历史等 | 不在三个痛点里 |
| 图形设置窗口、多语言界面、自动更新 | 第一版用不上 |

## 6. 平台规则下的边界

| 系统 | 规则 | 影响与处理 |
|---|---|---|
| macOS | 密码框等“安全输入”状态下，键盘监听失效；偶尔会被某些应用卡住不释放 | 输入法：系统在密码框里自动切回英文，属正常行为，其余不受影响。键鼠共享：键盘暂时转发不了，M8 提示 |
| macOS | 输入法必须是独立程序，由系统拉起和管理；首次安装要注销重登一次 | 一个安装包同时装好；关闭该功能 = 从系统输入法列表移除 |
| macOS | 屏幕录制权限：15 起约每月弹窗再确认；新截屏接口 14 起才有 | 最低 macOS 14；权限引导里提前说明 |
| macOS | 本地网络权限：15 起连接对端要授权 | 权限引导里说明；用正式签名 |
| macOS | 过不了 App Store 沙盒 | GitHub 下载，签名加公证 |
| Linux | 两套显示系统规则不同。X11 下三个功能都能按 macOS 的思路做 | 做 Linux 时先看你的机器是哪套 |
| Linux（Wayland） | 键鼠共享只能走系统门户：需要 GNOME 46 以上或 Plasma 6.1 以上，Sway、Hyprland 不可用，每次登录会话要弹一次授权；完整的剪贴板互通要更新的版本 | 满足版本要求才支持，否则只支持 X11，明说 |
| Linux（Wayland） | 截屏走系统门户，GNOME 上可能每次都弹"共享"确认；全局快捷键没有通用机制 | 快捷键改为在系统设置里绑定"启动截图"命令；弹窗属系统强制，明说 |
| Linux（Wayland） | 第三方程序不能全局监听按键 | 对输入法没有影响：输入法是通过框架拿到按键的，不需要全局监听 |
| Linux | 输入法框架不止一种（Fcitx5、IBus），输入法外壳要按框架的规范各写一份 | 先支持你机器上用的那一种；引擎和词库与 macOS 共用 |
| Windows | 在锁屏、权限确认弹窗时接收键鼠通常要装系统服务 | M0 小样确认；做不到的场景明说 |
| 三个系统 | "粘贴时才拉取文件"各系统机制不同，不一定都能做到 | M0 最先验证；做不到的方向用"发送到另一台" |

## 7. 性能（F2）

常驻主进程一个（系统原生，不含网页内核；macOS 上用 Swift 写），截图和键鼠共享编译在里面，没开的不初始化。输入法按系统规定是另一个独立进程，启用后由系统拉起，引擎和词库只在这个进程里。

| 功能 | 关闭 | 待命 | 工作中 |
|---|---|---|---|
| 输入法 | 已从系统输入法列表移除，进程不存在 | 英文状态，按键直通 | 中文状态，引擎查词 |
| 截图 | 不初始化 | 只向系统登记 1 个快捷键 | 截屏和标注；结束后图像内存全部释放 |
| 键鼠共享 | 不开端口、不拦截 | 开端口，监听鼠标移动做边缘判断 | 光标在对端时才拦截并转发 |

**预算（目标值，M0 实测后校准；超标先修再交付）。** 内存以系统任务管理工具里该进程的内存为准。

| 场景 | 内存 | CPU / 延迟 |
|---|---|---|
| 主进程，功能全关 | ≤ 20 MB | 空闲 0% |
| 主进程，截图和键鼠共享待命 | ≤ 35 MB | 空闲平均 ≤ 0.1% |
| 输入法进程 | ≤ 150 MB（取决于词库） | Shift 切换即时（≤ 20 ms）；按键到候选出现 ≤ 20 ms；英文状态约 0% |
| 截图 | 结束后 5 秒内回落 | 快捷键到选区界面出现：单屏 ≤ 200 ms；多块 4K 屏或开机后首次 ≤ 400 ms |
| 键鼠共享（控制对端时） | — | 软件自身处理延迟 ≤ 2 ms（按 95% 的事件统计，不含网络）；CPU ≤ 单核 3% |
| 安装包 | ≤ 40 MB（含基础词库） | — |

## 8. 实现设计

**代码组织：** 一个仓库。跨系统的逻辑（配置、键鼠共享协议、剪贴板与文件传输、长截屏拼接、截图标注）放核心包，三个系统共用；和系统打交道的代码（监听按键、截屏、注入键鼠、输入法外壳）各系统一个适配包。

**按键处理顺序：** ① 本软件的快捷键（截图、紧急拉回）；② 键鼠共享：光标在对端时把原始按键发过去；③ 其余按键原样交给系统，输入法从系统那里拿到按键。

**语言分工（v0.9 按实际更新）：** 和系统打交道的部分用各系统的原生语言写——macOS 上输入法外壳、菜单栏、截图都是 Swift，引擎衔接和纠错是 C（引擎的接口本身就是 C，这样最稳最省）。Rust 留给三个系统共用的部分：键鼠共享的协议和传输。

**输入法：** 引擎用开源的 librime（拼音转换、整句、自学习都是引擎自带）；每个系统写一个很薄的外壳，负责收按键、显示候选窗、把文字提交给应用。词库和配置各系统共用。
- “单击 Shift”由外壳判定后再交给引擎切换：引擎看不到 ⇧⌃A 这类组合键和按着 Shift 点鼠标，交给它判会误切。
- 纠错分两层。引擎里：只收“不可能是正常输入”的敲反、少敲、连敲拼法（规则由 `tools/gen_typo_rules.py` 从词库生成）。引擎外（`yw_fix.c`）：列出和输入只差一处的拼法，用词库词频打分，和“照原样读”（完整拼音、没打完、简拼混输）比，明显更常见才作为第二个候选提示。
- 引擎自带的邻键纠错实测会弄脏正常输入的候选（打 nihao 第二个变成“不好”），不启用。
- 整句：引擎自己组的整句有时不准（haikeyiba 给“还可一把”）。外壳用词库现成的词频另算一遍“词频乘积最大”的切法，三个字以上且和引擎首选不同时，把它放在候选最前面。56 句日常用语实测：引擎首选对 45 句，加上这个后对 50 句，没有改错的。不下载模型，内存多约 3 MB。
- 仍然不准的是要看上下文的同音字（的/得、在/再、一边/一遍），这要真正的语言模型。开源的万象语法模型文件约 390 MB，内存估计多占一百到几百 MB，会超过预算，你定了先不上。
- 增强词库（2026-11-12 落地）：加装雾凇拼音（全套 188 万词）。`tools/get_dict.sh` 下载到 `third_party/rime-ice/`（不入库），`tools/make_dict.py` 在构建时生成引擎用的词库；个人词库沿用原名不丢。实测：换词库后首次启动编译约 4 秒，常驻内存不变（约 34 MB，词库是按需映射的）；56 句日常用语引擎首选对 52 句。雾凇的权重是人工调的排序值（单字和词不在一个量级），拿来“另算整句”会改错 4 句，所以用大词库时关掉另算整句；纠错层的词频仍取自带小词库。独立评审（另一个 AI 对着 librime 1.17 源码和真实词库核对）：自动注音、附加词库、个人词库沿用、lve/nve 两种打法都核实无误，无高风险；报的 7 条已全部处理——下载先写临时文件再替换（断线不留半截）、词库版本号改为来源指纹（不再每天无故重编）、自带词库的生僻字按词频排并补回 119 个少见读音、生成的词库写明来源和改动、基础模式会删掉全套的两个文件、测试补 5 项（共 46 项）。
- 候选横排：左右键和 Tab 在候选之间移动，上下键翻页。整句、纠错这两种外壳自己加的候选，高亮和选中由外壳管（引擎不知道它们）。

**截图：**
- 普通截图：快捷键 → 抓取所有屏幕 → 全屏窗口显示冻结画面 → 框选 → 标注 → 输出 → 释放。
- 长截屏是另一套实时流程：画面不冻结，滚动要穿透到下面的窗口，按相邻两帧重叠区域拼接。
- 长截屏的实际做法（macOS）：入口是工具条上的一个按钮（先框选再点），不是界面稿里的顶部切换。每 0.12 秒截一次选区，把每行横向压成 16 个灰度值当“行特征”，找出新旧两帧错开多少行对得上，把新露出来的行接到下面。顶部、底部固定不动的栏在第一次接上时认出来：比对时避开，底栏只在最后补一次。只认向下滚；对不上就不接并提示；最长 20000 像素。已知局限：大片空白可能接少；页尾回弹可能接进一段空白。
- 长截屏补充（参考 Shottr 的自动/手动两种模式）：框选整个窗口时，先找出哪几列在动，只拿会滚动的那一栏来比、来接（侧栏不进长图）；接好的每一段压成 PNG 存放以省内存；“自动滚动”和“回到断点”由一苇向页面发滚轮事件，需要“辅助功能”权限，第一次用时才申请。
- 点选补充：桌面小组件、菜单、弹出框按窗口识别；通知横幅这类画在系统整屏层里的小块，靠“辅助功能”接口按鼠标位置查询，没有权限时不可选。
- 文字标注：就地出现一个输入框，回车或点别处落定；Esc 只取消这段字（输入法正在拼字时只丢掉没拼完的）。
- 点选窗口：还没框选时鼠标指到哪个窗口就高亮哪个，点一下选中整个窗口。
- 提取文字（v0.17，`apps/yiwei-macos/OCR.swift` 和 Overlay.swift 的“提取文字”一节）：点了按钮才识别，用系统的 Vision（中文、英文），识别框里的原图（不带标注），在后台线程算。系统给的是每个字的框，按“从上到下分排、排里从左到右”排好，拖选就是选这串字里的一段；复制时换排换行、同一排里两段之间隔一个空格。这期间框不能动、标注工具和撤销重做停用。实测一次约 0.1 秒；这台 Mac 上头几次有过约 20 秒（系统在准备识别模型），之后都快。
  - 验证：自检 4 项（三行中英数字认对、每个字的位置对、选一段拼出来的字对），另用程序画了一张“提取文字”状态的图看过。**真的在屏幕上拖选、按 ⌘C 这一步没有自动测，等用户试。**
  - 独立评审（没参与编写的评审者只读了代码）：没发现会崩溃或留下脏状态的问题。已改：拖着选字时左边小条的字被裁（宽度定死）；单击会选中 1 个字、手抖就选上（改成拖出 3 个点才开始选，单击是取消选中）；⌘A、⌘C 认键位不认字母（改认字母）；提取文字时撤销还能删标注（停用）；三击缩回 1 个字；识别完指针不更新。没改、记着的：并排两栏一起框时同高的两段会并成一排，选和复制会左右串；网址、代码、编号可能被系统“纠正”成别的字；整屏框选时很小的字可能漏认、被工具条盖住的字选不到；竖排和旋转的字位置不准。
- 截图界面的做法在 M0 用小样定：优先一套代码同时跑 macOS 和 Linux；硬条件是按下就出、文字标注能正常打中文。

**键鼠共享：**
- 按键和鼠标键的按下抬起走可靠通道（丢一个"抬起"会卡键）；鼠标移动和滚轮走不重传的快速通道；剪贴板和文件走可靠通道，大文件不挤占键鼠。
- **鼠标被控切回**（v0.16，你提的开关，默认关）：关着时和原来一样，别的电脑的指针在这台上，这台自己的鼠标照常能用，两边动的是同一个指针。开关管的是“这台去控制别的电脑时”（你定的）：甲开着，甲的指针在乙上时，乙自己的鼠标（触控板）真动起来了——0.4 秒里合起来挪了 30 像素以上，轻轻碰一下不算，敲键盘不算——甲的指针就回甲自己这边，落在出去的那条边往里一点（和别的电脑来接手时一样，你定的），乙的指针留在原地归乙用；甲想再过去，重新从边上穿过去。乙开没开不影响甲。开关在“展开”里，每台各设各的。
- **剪贴板跟着指针走**（v0.14 定，你提的规则；甲是拿着键鼠的那台，乙、丙是指针进去的那台）：
  1. 甲的指针进到乙：乙的剪贴板临时换成甲的那份。
  2. 甲的指针在乙上时复制的东西：指针回到甲、或者直接去丙，跟着走。
  3. 甲的指针离开乙：乙的剪贴板恢复成甲来之前的样子（用乙自己的键鼠粘贴不到甲带来的）。
  4. 甲在乙上什么都没复制：回来后甲的剪贴板不变。

  做法：乙在甲的指针进来时把自己的剪贴板整份存下（所有格式），甲走了放回去；甲带来的那份按电脑记着，甲的指针在乙上时才放进剪贴板，甲没复制新东西再进来就不用重传。甲走的时候剪贴板里的内容和原来不一样就算“在乙上复制过”，带回给甲；甲这时指针已经到了丙，就接着带给丙。带的是文字和图片（两样都有就都带），每次带都标上“是带过来的还是带回去的、第几次带”，收的一方不用猜；复制的是文件、文件夹时，合起来 100MB、2000 个以内就整批带过去（原件不动，对面收在临时文件夹里，当成“复制了这几个文件”），更大的不带并提示改用“发送文件”。甲带到乙的那份不进乙的剪贴板历史。规则写在核心的 `clipflow` 里（Windows、以后的 Linux 共用），Mac 外壳用 Swift 另写了同样的一套，两处各有自检。已知的限制见《键鼠共享进度》同名一节。
- 传输（v0.9 定）：没有用 QUIC，原因是它要带一大套依赖，而我们要的只是“输入不等重传”。鼠标和键盘走 UDP 加自己很小的一层补包：鼠标移动和滚轮每个包带“从开始到现在一共移了多少”（丢了用下一个，旧包晚到就扔，不会少走也不会多走），按键和点击在每个包里重复带上对方还没确认的那几次，并带着它发生那一刻的鼠标累计量（先把鼠标走到位再点）；鼠标在动时不要对方逐包确认，停下后最后的累计量要确认。剪贴板、文件、位置同步走 TCP。老牌的 Synergy、Deskflow 全走 TCP，无线网丢包时会卡；较新的 Lan Mouse 和游戏串流的 Moonlight 走 UDP。模拟丢包自测：丢包 5%～20% 时按键不丢不乱，最慢晚到 14～20 毫秒。
- 加密和入组（2026-11-13 第三次定，取代“两边核对 6 位数字”和同一天做过的“介绍”）：Noise 协议（XX 模式，`snow` 库）握手，之后 TCP、UDP 两条通道共用握手得到的密钥、包号各占一半号段。几台电脑是一“组”：
  1. 一组有三样：校验码（8 位，去掉了易混的字符，给人看、给人输入）、组钥匙（随机 32 字节，人不用管）、第几版。没加入别人的电脑自己就是一组。
  2. 组员互认不用人管：连上后各自出示“我有组钥匙”的证明（和这次握手绑在一起，别人抄不走、不能原样弹回来）；广播里带一个只有同组算得出的记号，同组的发现了就自动连。所以加入时没开机的组员，以后开机也自动连上。
  3. 加入：在要加入的那台上输入对方的校验码，两边用 SPAKE2（`spake2` 库，MIT/Apache-2.0）核对“知道的是同一个码”——码不在网络上传，旁听的拿不到，冒充的每连一次只能猜一个；连着错 5 次停 1 分钟。码对了，被找的那台弹一次“允许吗”，允许后把校验码和组钥匙通过加密连接交给新成员。找组里哪一台都行，找谁谁同意。
  4. 换组只带自己：加入别的组时离开原来的组（连接断开、摆法从头来），原来组里的电脑不动。
  5. 请出一台 / 换校验码：这一组生成新的校验码和组钥匙（版本加一），发给连着的组员（不发给被请出去的那台）；组员只跟着更新的换。当时没连着的组员要用新码重新加入一次。
  - 代价和取舍：组里任何一台都能让新成员进来、都能换码（家里几台自己的电脑，这个程度够了；Mouse Without Borders 也是全组一把钥匙）。旧版配对过的电脑升级后各自成一组，要重新加入一次。
- 共用核心在 `core/`（Rust）：消息格式、位置关系、按键对照、输入通道、加密配对、控制权、连网，目前 79 项测试。
- 监听回调里不加密、不发网络、不写日志、不等任何会被占住的锁：只读几个原子量、把事件放进定长队列，由核心的后台线程处理（2026-11-13 落地，之前的实现没做到这一条，是真机上“一卡一卡”的头号原因）。系统停用监听时自动恢复。
- 控制权（2026-11-13 第二次定，取代同一天早些时候的“本机直连键鼠优先”）：照 Lan Mouse 的对称做法，发送照 Moonlight。要点：
  1. 没有主从，也不分谁优先。鼠标发的是移动量，被控的那台加在自己指针现在的位置上；所以被控那台自己的键鼠照常能用，两边的鼠标动的是同一个指针，像一台电脑插了两个鼠标。原来“本机一动就把对方请回去”的判断全部删掉——它要靠猜（多大的移动算“本机在用”），真机上两边互相赶，是卡顿和冲突的一个来源。
  2. 鼠标什么时候回去，由被控的那台看：指针真走到了它屏幕的边，它告诉控制方“到这条边的这个位置了”；回本机、接着穿到第三台、还是不动，由控制方按摆法定。控制方不用再估计对方的指针在哪。
  3. 谁最后穿过边谁控制：收到别的电脑“我进来了”，自己的鼠标正在别处就先放开回本机；自己的鼠标要穿出去时，先请正在本机上的那台回去。一台电脑同一时刻要么自己的鼠标在别处、要么有一台别的电脑的鼠标在它这里。每次穿屏带序号，过期的话不理。
  4. 发送：监听回调只放队列；后台线程把攒着的移动合成一次再发（鼠标每秒一千次也只发得动的那么多）；被控方来不及照做时，排着队的移动加起来一次做完，一点不少走。
  - 没有照搬的地方：Lan Mouse 不做剪贴板和文件，我们有；它在 Windows 上用相对移动注入，我们仍然告诉外壳“把指针放到哪”（外壳接口不用改）。GPL 项目只读文档和代码理解做法，没有搬源码。

**协议合规：** 依赖只用 MIT、Apache-2.0、BSD 等宽松协议（白名单，其余构建失败）。librime 是 BSD 协议，可直接用；基础词库用 rime-pinyin-simp（Apache-2.0，源自 Android 开源拼音），随包分发并附声明；增强词库雾凇拼音是 GPL，不入库不打包，由用户可选下载。Deskflow、Lan Mouse、鼠须管、小企鹅等 GPL 项目只参考公开文档和软件行为，不照抄、不搬运源码。仓库带第三方声明文件。（我不是律师，这是开源项目的通行做法。）
